## 当前架构的痛点在哪？

用一句话概括现在的模式：**"这就像把产品经理、架构师、初级前端和测试工程师四个人的活儿，全塞进了一份近一万字的需求文档里，然后丢给一个刚睡醒的应届生（大模型），指望他一次性把活干完还不出错。"**

1.  **注意力稀释 (Attention Dilution)**
    *   **现象**：AI 经常会漏掉 Shadcn 的规范，或者写出幻觉代码。
    *   **原因**：大模型的"注意力"像聚光灯，当你的 `PROMPT`（近 9KB）里有几百条规则时，聚光灯就散了。模型在处理第 80 条规则时，可能已经忘了第 2 条。
2.  **上下文雪崩 (Context Avalanche)**
    *   **现象**：生成越来越慢，API Token（也就是钱）消耗巨大。
    *   **原因**：每次对话，我们都把完整的报错日志、长长的文件内容丢给它，外加那个巨大的 `PROMPT`。由于它是无状态的，每次都要从头读一遍这些历史信息。
3.  **单体架构的脆弱性 (Monolithic Fragility)**
    *   **现象**：经常是一锤子买卖，或者在 `maxIter: 15` 的循环里盲目乱撞，改不好 bug。
    *   **原因**：目前只有一个 `codeAgent` 在既当爹又当妈。没有专门负责"审题拆解"的 Planner，也没有专门负责"验收跑通"的 Reviewer/QA。

## 新旧架构一览对比

| 维度 | 当前做法 (v1) | 业界更优方案 (v2) |
|------|-------------|------------------|
| **Prompt** | 1 个 ~9KB 的超级 System Prompt | **分层 Prompt**：基础角色 + 按任务阶段动态注入 |
| **Agent** | 单 Agent 死循环 (`maxIter: 15`) | **多 Agent 协作**：Planner -> Coder -> Reviewer |
| **上下文** | 全量堆在对话历史里 | **摘要压缩** + 仅传递关键文件片段 (RAG) |
| **模型** | 统一用一个模型 | **分级调用**：简单任务用小模型，核心生成用强模型 |
| **反馈循环** | 靠 `summary` 字段盲跳出 | **自动测试驱动**：写完立刻跑 lint/build，失败才重试 |

## 业界最前沿（2026年）的 AI Coding 架构演进方向

当我们学完本教程，把所有积木（Next.js API, tRPC, Inngest, E2B）的基础都摸透后，就可以对业务逻辑层进行**现代化改造**。进阶方向是把目前的**单体脚本流 (Monolithic Agent)** 升级为**多智能体协作与 RAG 注入管道 (Multi-Agent Pipeline with Dynamic Context)**。

### 改造一：Prompt 与记忆的"瘦身抽屉" (Context Separation)
*   **传统做法**：一个 9KB 的超级 Prompt，永远背在身上。
*   **现代做法**：
    *   **System Prompt (核心人设)**：极简，约 200 Tokens，只定义"你是 TypeScript 高级工程师，绝不使用 any"这种核心底线。
    *   **Tool Descriptions (工具包说明书)**：把"Shadcn 怎么导入"、"tailwind 怎么写"的规则，写到 `createTool` 的 `description` 里。大模型**只有在决定使用这个前端工具时，才会临时拉取这部分记忆**。也就是"关注点分离"。
    *   **RAG 动态注入 (Retrieval-Augmented Generation)**：当 AI 说要改 `button.tsx`，我们只把 `button.tsx` 的最近几行和它的 TypeScript 接口发给它，而不是扔给它整个项目的上下文。

### 改造二：引入多智能体工程化协作流 (Multi-Agent Swarm)
不要再用一个模型跑到底，我们要基于 Inngest 的可靠性，搭建流水线：

1.  **The Planner (规划师 - 适合又快又准的模型，如 Claude 3.5 Haiku 或专调小模型)**
    *   **职责**：只看用户的需求，不写代码。它的产出是一张 JSON 格式的"施工蓝图"（比如：需要修改 `page.tsx`，新建 `header.tsx`，安装 `framer-motion`）。
2.  **The Coder (全栈开发 - 用最强的代码模型，如 Claude 3.5 Sonnet)**
    *   **职责**：不考虑其他事，拿到 Planner 的蓝图后，专心致志逐个文件写出高质量的 TypeScript 代码并调用写入工具。
3.  **The Reviewer (代码审查与测试 - 严谨模型 + 终端执行)**
    *   **职责**：Coder 写完，触发 Reviewer。Reviewer 自动在终端跑 `pnpm type-check` 和 `pnpm lint`。没报错，才通知前端更新；报错了，把极简版错误日志发回给 Coder 修改。

### 改造三：从"死循环"走向事件驱动流 (Event-Driven State Machine)
*   目前在 `functions.ts` 里，你是用 `createNetwork` 的 `router` 做了一个基于状态的 `while` 循环（靠 `summary` 字段跳出），这在出故障时很难排查是第几步挂了。
*   **进阶做法**：利用 Inngest 原生的强大能力，把步骤变成独立的云函数。
    `step.run('planner')` -> `step.run('coder')` -> `step.run('tester')`
    这样哪怕 E2B 突然断网，Inngest 也能精准地在 `coder` 那一步自动重试，而不需要把整个 Agent 流从头再跑一遍。

## 给独立开发者的学习地图 (从 0 到 1 再到 N)

为了实现高薪远程工作或自主 SaaS 产品的目标，我们要始终保持**工程优雅**与**商业落地速度**的平衡。

**当前阶段（先用后懂，建立肌肉记忆）**
*   **核心任务**：放下完美的执念，跟着这个老架构把教程死磕到底。
*   **你需要得到什么**：
    1.  Next.js 15 App Router 的宏观概念（哪些在服务端跑，哪些送给客户端，以及 `use client` 到底意味着什么边界）。
    2.  tRPC 的极度舒适体验：一次定义，前后端类型永不脱节。
    3.  Inngest 处理长时间 AI 任务的"保活"机制（如果不用 Inngest，AI 生成超过 60 秒 Vercel 等平台就会直接切断连接）。
    4.  E2B 远程沙盒的控制权。

**第二阶段（架构大洗牌）**
*   **核心任务**：基于这套指南，推翻 `functions.ts` 中的 Agent 逻辑，亲手写出一个现代化的 Planner -> Coder 管道。
*   **技术栈侧重**：
    1.  **Vercel AI SDK (`ai` 包)**：研究 `generateText` / `streamText` 和原生 Tool Calling。它比 `@inngest/agent-kit` 更底层、更灵活，是目前业界做 AI 应用的主流标准。推荐用它替换掉 `createAgent`。
    2.  **保留 Inngest 作为调度层**：Inngest 的价值不在于 Agent-Kit，而在于它的**持久化执行、自动重试、事件编排**能力。用 Inngest 的 `step.run` 串联 Vercel AI SDK 的调用，是目前最稳健的全栈 AI 后台方案。
    3.  **尝试将 `createNetwork` 的单循环改为 Inngest 的多步骤 (`step.run`)**：`step.run('plan')` -> `step.run('code')` -> `step.run('review')`，每一步独立可重试。

**第三阶段（商业视角与进阶技术）**
*   **上下文工程 (Context Engineering)**："如果不优化，现在的这种长 Prompt 会让你亏死。如果上线成为 SaaS，每一次简单的对话都在消耗巨大且无意义的 Token。未来产品的核心竞争力在于：**如何用最小的 Token 注入，唤醒模型做最精确的输出。**"
*   **混合模型策略**：将高昂成本的强模型（写代码）和低成本高确定性的小模型（做规划、做审查）混合使用，才是区分初级开发者和架构师的分水岭。
*   **RAG (检索增强生成) 入门**：让 Agent 学会自己"搜索"官方文档或现有的项目代码片段，按需注入上下文，而不是依靠你提前硬编码所有规则进 Prompt。这是告别"巨型 Prompt"的终极方案。

## 面试高频追问（收藏备用）

| 面试官可能问的问题 | 架构师级别的回答要点 |
|---|---|
| 为什么不用一个长 Prompt 搞定所有事？ | 长 Prompt 是一种 implicit control flow，用自然语言描述了所有分支逻辑，但模型的注意力窗口有限。正确做法是把 control flow 交给代码（路由逻辑、多 Agent 编排），只给模型当前步骤需要的最小上下文。这本质上是**关注点分离**在 AI 系统中的体现。 |
| 为什么要用 Inngest 而不是简单的 Webhook？ | Webhook 是"发射后不管"。Inngest 提供了：1) 持久化执行（函数跑 5 分钟也不会超时）；2) 自动重试（E2B 断网了会从断点恢复）；3) 可观测性（能在 Dashboard 看到每一步的执行状态）。这是生产级 AI 应用的必备基础设施。 |
| 如何控制 AI Coding 产品的成本？ | 三个维度：1) 分级模型调用（小事用小模型）；2) 上下文压缩（摘要替代全文）；3) 缓存机制（同样的 Shadcn 规则不要每次都发给模型）。 |

> **寄语**：代码这东西，早期的笨方法就是用来踩坑的。你现在不仅"知道它慢和差"，还"切身体会到了它为什么慢和差"，这就是最宝贵的经验。继续前进吧！
